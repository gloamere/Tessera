# 视觉评审

评审具体产物是否清楚、可信且符合使用语境，并把观察转成可执行修改。结论必须指向可见证据，不把个人偏好包装成通用规则。

## 适用边界

- 输入应包含可查看的页面、截图、设计稿、组件、代码实现或明确的视觉方案。
- 从零定义 token、页面结构和技术栈约束时使用 `$gloamere-ui-system`。
- 只改文章措辞、品牌语气或营销文案时，不调用本 Skill。
- 没有足够视觉证据时，说明缺少什么；不要凭空推断界面质量。

## 评审步骤

1. 确认受众、核心任务、品牌气质、设备与当前完成度。缺失信息只影响局部判断时，显式写出假设并继续。
2. 先描述观察到的事实，再解释它如何影响理解、操作或信任。把截图可见事实、代码推断和待验证项分开。
3. 只评审与当前产物相关的维度：
   - 信息层级：首要任务是否突出，阅读顺序是否稳定。
   - 密度与节奏：分组、间距和内容量是否匹配使用频率。
   - 排版与语言：字号、行高、对齐和界面短文案是否协同。
   - 色彩与对比：语义、品牌、状态和可读性是否一致。
   - 组件一致性：token、控件形态和交互反馈是否复用同一规则。
   - 状态完整性：loading、empty、error、disabled、hover、focus 和 reduced-motion 是否被处理。
4. 按用户影响、出现频率、修复成本和连锁风险排序。不要为了填满维度而机械打分。
5. 每项建议写清修改对象、问题原因、具体动作和验证方式；能复用 token 或组件时，不给孤立像素补丁。

## 输出契约

依次给出：

1. 一句话结论，以及当前最影响体验的原因。
2. 关键证据：保留项、问题项和无法确认项。
3. 按 P0/P1/P2 排序的修改建议；默认最多列出三个最高价值改动。
4. 修改后的验收方式，包括必要的响应式、键盘与对比度检查。

渐变、对称、圆角、阴影或高密度本身都不是错误；只有它们与任务、品牌或可用性目标冲突时才提出调整。避免“更高级”“更有设计感”这类无法验证的建议。
